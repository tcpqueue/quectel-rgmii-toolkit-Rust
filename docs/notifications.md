# 消息通知

“消息 → 消息通知”。通知渠道统一在这里配置，短信转发和断网恢复通知分别选择使用哪些渠道。旧的 `#forwarding` 地址会跳到这一页。

## 渠道

Server酱 Turbo、企业微信、钉钉、飞书、Webhook、本卡短信，凭据格式见 [短信服务与转发](sms.md#配置)。渠道打开并填好凭据才算可用；未配置的渠道在选择处标为“未配置”。可用“测试推送”验证（本卡短信除外）。

## 短信转发

打开“短信转发”并选择渠道。升级前的配置没有渠道选择，默认使用全部渠道，与以前一样只推送到已启用的渠道。转发行为见 [短信服务与转发](sms.md#转发行为)。

## 断网恢复通知

网络恢复后发送一次，内容包括断网时间、恢复时间和断网时长：

```text
[RM520N-EU] 网络已恢复
断网时间: 2026-10-11 16:27:13 (UTC+8)
恢复时间: 2026-10-11 16:27:52 (UTC+8)
断网时长: 39 秒
```

- 断网由总览的延迟监测判断，需要开启延迟监测。连续失败 10 秒记为断网，恢复后按“断网至少多久才通知”（默认 60 秒，10–3600）决定是否发送。
- 时间按保存设置时浏览器的时区显示，语言跟随当时的界面语言。模块系统时钟在断网期间被校时导致恢复时间早于断网时间时，不发送。
- 看门狗重启模块前会保存断网开始时间，重启后的这次断网仍从原开始时间计算，恢复时通知一次。
- 推送失败会在 3 分钟内重试；修改渠道或开关会清空待发队列。

Webhook 收到的格式：

```json
{
  "event": "network.restored",
  "id": "outage-1791707233757",
  "device": "RM520N-EU",
  "lost_at": "2026-10-11T08:27:13.757+00:00",
  "restored_at": "2026-10-11T08:27:52.813+00:00",
  "seconds": 39,
  "text": "断网时间: …",
  "part": 1,
  "parts": 1
}
```

请求带 `Idempotency-Key: <id>-<part>`。

## 近期推送

最近 50 条结果，类型分为短信、断网恢复、测试。

## 验证

- 模拟服务：Webhook 接收端收到测试推送、转发短信和断网恢复通知；只发往为断网通知选择的渠道；断网短于阈值不发送。
- RM520N-EU 真机：开启飞行模式约 25 秒制造真实断网，断网 39 秒，恢复后 1 秒内送达模块本机的 Webhook 接收端，时间与时长正确。测试期间短信转发和本卡短信渠道均关闭，没有发送短信。
